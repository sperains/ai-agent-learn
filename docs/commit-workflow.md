# 提交与接续规则

Git 提交是学习过程的恢复点，不是每次输入代码后的自动动作。提交的目标是让未来的自己能够知道“学到了什么、验证了什么、下一步是什么”。

## 基本原则

1. 不自动提交，也不自动推送；只有学习者明确要求时才执行。
2. 提交前必须检查工作区、测试结果、课程日志和当前进度。
3. 一个提交对应一个完整学习单元，避免把多个无关主题混在一起。
4. 不提交 `.env`、真实密钥、个人数据、临时缓存和生成目录。
5. 未通过测试的实验默认不作为稳定学习成果提交；如果确实需要保存，必须在提交说明中明确“验证未通过”和原因。

## 推荐提交时机

### 课次完成后

当以下内容完整时，建议提交一次：

- 本课实验代码；
- 正常路径和失败场景测试；
- 本课学习日志或复盘；
- `docs/progress.md` 的状态、证据和下一步；
- `uv run pytest` 等验证命令的结果。

推荐粒度：一课一个提交。纯概念课可以两课合并；实验较大的课可以拆成“设计”和“实现”，但必须保持每个提交可解释。

### 四课批次完成后

第 4、8、12 课等批次节点需要额外做一次质量门禁。通过后建议提交一个批次总结，记录四课成果、复习结果、遗留问题和下一批计划。

### 阶段验收后

阶段验收应形成一个明确的里程碑提交，包含：

- 阶段证据包；
- 综合项目增量；
- 回归测试结果；
- 质量评分；
- 阶段复盘。

## 提醒时机

学习助手在以下时机提醒，但只提出建议，不代替学习者提交：

1. 开始新课前：上一课有完整改动但尚未提交。
2. 一课验证通过后：代码、测试、日志和进度已经形成完整单元。
3. 四课批次结束后：达到批次门禁且工作区存在相关改动。
4. 阶段验收前：发现未提交改动可能混入多个学习主题。
5. 用户要求切换方向、暂停学习或继续下一阶段时：先提示当前未提交内容和风险。

不在以下时机打断：

- 正在排查一个失败实验；
- 只修改了临时调试代码；
- 课程尚未完成核心验证；
- 用户明确说暂不提交。

## 提交前检查清单

```text
git status --short
uv run pytest
git diff --check
确认没有环境文件、密钥和无关改动
确认学习日志、进度和证据链接已同步
```

## 提交信息格式

遵循项目约定：

```text
type(scope): 中文标题

1. 中文说明第一项真实改动
2. 中文说明第二项真实改动
```

学习提交示例：

```text
feat(agent): 完成第一次模型调用实验

1. 增加可替换的模型调用接口和固定响应实现
2. 补充请求响应事件链、错误场景测试和第一课复盘
3. 更新学习进度中的课程证据与下一步
```

## 分支策略

默认在 `main` 上保持已验证的学习成果。需要进行高风险重构或长时间实验时，先创建主题分支；实验完成并通过验证后再合并。不要为了保存半成品而频繁向远程推送未经验证的内容。
