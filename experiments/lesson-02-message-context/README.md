## 目标

完成本课后，能够说明模型每次只能读取应用传入的上下文快照，正确保存成功对话的用户和模型消息，并以固定顺序构造下一轮请求。

## 概念边界

`Conversation.history` 是应用层保存的状态。模型看不到这段状态，也看不到应用的处理逻辑，只有 `build_request` 返回的消息列表会被传入本轮模型调用。

角色标记消息的来源和语义位置。`system` 表示每轮调用都要重新带上的长期行为边界，`user` 表示当轮用户需求，`assistant` 表示模型已给出的历史回答。角色不是模型的永久记忆，也不能代替应用层的权限控制。

一次正常轮次在模型成功返回后才写入历史。如果调用失败，不能追加看似完整的 `user + assistant` 对话轮次。失败请求可在生产系统中另行审计或重试，但不属于本课的正常历史。

## 核心事件链

```text
应用读取已保存的历史
  → 追加 system 规则与当前 user 消息，构造本轮上下文快照
  → 调用模型
  → 成功：保存本轮 user 与 assistant 消息
  → 失败：不追加完整对话轮次，交给错误处理
  → 下一轮从已保存的成功历史重新开始
```

一轮请求的消息顺序为：

```text
system → 历史 user → 历史 assistant → 当前 user
```

## 实验与验证

业务实现位于 [src/main.py](src/main.py)，测试位于 [tests/test_lesson_02_message_context.py](tests/test_lesson_02_message_context.py)。

测试覆盖：

- 已保存历史和当前用户消息按预期顺序构成请求；
- 成功轮次同时保存用户消息和模型回答；
- 首轮请求只有 `system` 和当前 `user`，不会伪造历史；
- 当前用户消息为空时抛出 `ValueError("当前用户消息不能为空")`。

执行：

```bash
uv run pytest
```

2026-08-27 的结果为 `8 passed`，其中第 2 课有 4 项测试。测试按绝对路径隔离加载各课的 `main.py`，避免不同实验的同名模块相互污染。

## 学习者的掌握证据

- 能说明模型只看到本轮组装的消息，看不到应用内部保存的历史和处理逻辑。
- 能说明不携带历史会丢失全局规则、上一轮用户问题和模型回答。
- 能说明失败调用没有模型回答，不能写入完整对话轮次。
- 能说明 `system` 与 `user` 的区别在于长期行为边界和当轮需求，且 `system` 规则也需要每轮重新传入。
